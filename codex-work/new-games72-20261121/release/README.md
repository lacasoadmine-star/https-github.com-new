# Additive 72-game release validation

This package validates release evidence and models the decision to open **all 72 new games together**. It does not deploy, create a service, change existing games, alter accounts, or perform any financial operation. The actual registry is still a work inventory; a reserved path or `RELEASE_READY` label cannot make it a working game.

## Inputs and identity preservation

`validateRegistry(registry, baseline)` accepts the root registry schema `zplay/new-games72-registry/v1`. It requires exactly 72 ordered entries, unique normalized official names, unique provider/variant identities, and distinct internal IDs, routes, module paths, evaluator/configuration paths and asset namespaces. Launcher category variations cannot inflate the provider-variant count. Punctuation/case variations in names and trailing-slash aliases in routes do not create extra games.

The baseline adapter is an explicit object containing nonempty `gameIds`, `routes` and `assetPrefixes` arrays, with optional additional provenance. Root's `../preservation/baseline.json` already has those fields. The validator rejects overlaps with this preserved inventory. A root namespace, overlapping new route prefix, reused game ID or reused asset prefix fails closed.

Baseline validation establishes consistency against the supplied source inventory. It does not establish that the inventory includes every currently deployed Worker module or dynamic backend record. The actual baseline's own scope and `activationRequiresFreshLiveBaseline` requirement remain in force. Root must obtain fresh live inventories before deployment.

## Release evidence contract

`reviewRelease({registry, baseline, attestationManifest, readArtifact, policy})` produces a review result. `readArtifact(path)` must return the actual bytes for a safe relative path. `fileArtifactReader(root)` supplies a filesystem reader that rejects traversal and symlink escape. Every artifact descriptor has:

```js
{ path, sha256, byteLength, mediaType }
```

The gate recomputes the byte hash and length. JSON evidence is parsed from those verified bytes. Missing files, wrong hashes, incomplete metadata, mismatched source identity and incomplete game sets all close the release.

The manifest schema is `zplay/new-games72-release-evidence/v1`, with:

- `releaseId`, matching the registry.
- `sourceCommit`, a full Git commit identifier.
- `frontendVersion` and `backendVersion`.
- `registrySha256` and `baselineSha256`, obtained through exported `hashObject()` over the exact input objects.
- `games`, containing one evidence entry for each of the 72 IDs, without aliases or omissions.

Each game entry supplies:

| Field | Required material |
| --- | --- |
| `gameId`, `sourceAuthors` | The target and implementation producer/task identities. |
| `pins.frontend` | Built frontend or module entry bytes under the registry's module path. |
| `pins.backendConfiguration`, `pins.evaluator` | Exact per-game backend configuration and evaluator bytes. |
| `pins.rules`, `pins.assets` | Verified rules specification and runtime asset manifest. |
| `references`, `referenceArtifactRoot` | Capture manifest at the registry's reference path and the root containing its actual media. |
| `mathAudit` | Independent probability, payout, money precision, version and maximum-win verification. |
| `reports` | Separate `unit`, `integration`, `ledger`, `mobile`, `lifecycle` and `recovery` reports. |
| `comparison` | Known-action comparison tied to this capture and this frontend. |
| `defects` | All recorded defects, each closed with a verified passing retest. |
| `rightsReview` | Per-asset permission/license/original-ownership evidence. |
| `releaseReview` | Peer review of the exact audit, tests, comparison, defects and rights records. |

`releaseSubject(registry, manifest, game, entry)` produces the precise input identity used by reports. Its hash includes source commit, game ID, frontend/backend/rules/engine versions, reference hash and all five source pin hashes. A report for different code or a different reference cannot satisfy this release.

No gameplay, payout evaluator, runtime asset or official observation is generated by this package. The entries in `release-gate.test.mjs` are synthetic in-memory fixtures for validator tests only; they are not saved as real per-game evidence and cannot be counted as completed work.

## Reference capture compatibility

The gate reads the existing `capture/evidence-capture.mjs` format directly: `schemaVersion: 1`, rounds, actions, controls and artifact metadata. It independently validates the important relationships and reads the actual artifact bytes instead of accepting the helper's status alone.

There must be at least seven distinct individually initiated and completed round observations, each linked to exactly one recorded input attempt. Every observation needs separate `before`, `afterInput` and `result` screenshot references, plus video coverage. When the capture environment reported audio recording support, corresponding audio evidence is required. Repeated outcomes are allowed; the gate does not require unique screenshot hashes or forced wins. Extra AUTO/HOLD observations cannot substitute for individually initiated inputs.

The official game identity must match the registry's name and provider variant. The product/demo URLs must use explicitly configured official hosts, and the launch must be a public DEMO/DEMO_EXH route. Capture dates must meet the configured current-task reference window. Portrait/landscape and viewport metadata are checked. An unresolved capture action/control batch or current blocker fails.

Every inspected active control needs an observed response and its control screenshot. The verified rules specification names the controls it requires, identifies all critical rules and cites actual hashed source documents; unresolved payout/bet rules cannot be hidden behind an empty checklist.

Media signatures establish file-type plausibility, not that a recording is decodable or depicts the claimed action. Independent comparison and review must inspect actual media. Hashes establish byte identity; they do not establish visual fidelity, timing, sound parity, asset rights or truthfulness by themselves.

## Reports and ordinary peer-review provenance

Report JSON contains `schema`, `gameId` and `subjectSha256`. Test reports include the command, isolated environment, explicit check results, and zero failed/skipped/cancelled required checks. Each check links to a hashed execution-evidence document bound to the same subject and test ID. Integration/ledger reports must identify a disposable isolated database; this package's own in-memory tests are not sufficient evidence for those per-game requirements.

The exported `requiredReportChecks` lists exact required checks, including concurrent/duplicate settlement, account ownership, accepted-response loss, same-key recovery, refresh, two tabs, 429 handling, mobile/orientation coverage, reduced motion and lifecycle cleanup. Tests may include additional checks. A failed check cannot be removed from the summary or relabelled as skipped to pass.

Math, rights and release review records have a `reviewerId`, `reviewedAt`, `conclusion: "APPROVED"` and `producerEvidence` artifact. The latter uses `zplay/new72-review-provenance/v1`:

```js
{
  schema: 'zplay/new72-review-provenance/v1',
  producerId, role, taskId, process, recordedAt,
  subjectSha256,
  inputSha256: [/* the actual reviewed input artifact hashes */]
}
```

`policy.reviewProducers` lists the operational producer/task identities assigned to the `math`, `rights` and `release` work. A reviewer/task cannot be listed as the implementation author of the same game. The review provenance must bind the appropriate evaluator/rules/check inputs, asset/grant inputs, or complete release-review inputs.

The source-check CLI reads this coordination roster from the optional `reviewProducers` field of the evidence manifest; when no completed review records exist, it uses empty lists. This field does not authenticate a person or authorize deployment by itself.

These are normal work records from the authorized implementation and peer-review process. **No new account, external identity service, cryptographic signature, manual user approval or additional confirmation is required.** A separate review agent or task can produce them. The role lists are project coordination data, not an authentication provider. The gate checks their consistency and the substantive linked evidence; an attributed name alone proves neither independence nor correctness.

A signature, hash, random seed or session identifier is not proof of fairness. This validator does not claim that an independent engine reproduces undisclosed provider RNG, reel strips or RTP. The math report explicitly distinguishes an independently audited operator model from provider certification.

## Activation and rollback boundaries

A result is `allowed: true` only when all 72 entries are ready and all corresponding evidence passes. There is no method to activate a successful subset. Failed or missing evidence leaves the release closed, even if 71 games passed.

`createNewGameGate({registry, baseline, review})` accepts only a successful result issued by the in-process reviewer for those exact inputs. A copied JSON object with `allowed: true` is not an issued review result. The resulting gate starts closed. `activate()` checks unchanged registry/baseline hashes and matching source/frontend/backend versions before opening all 72 flags together.

This is not live-runtime discovery: the caller must supply the genuinely fresh observed deployment inputs, and separately verify actual live versions. Importing the module, passing unit tests, uploading an artifact, or receiving a platform SUCCESS message does not activate or verify any game.

`disableNewRounds({gameIds, reason})` can affect only new IDs. It has no wallet, ledger, balance, deletion, reset, payout or refund operation. Old game IDs return `null` from gate checks so the existing handler continues to own them. Once a release is withdrawn, this instance cannot reactivate it.

`recoveryRouteAvailable(gameId)` remains true for the new IDs after disable. This is route availability only: existing authentication, ownership and accepted-round lookup must still execute. The backend must recover an already accepted request before applying the gate for a genuinely new wager. The gate cannot certify transaction integrity without those existing server controls. Its state is in memory; integration with the existing deployment's durable feature configuration remains separate work.

## Actual current-registry check

From the repository root:

```sh
node codex-work/new-games72-20261121/release/check-current-registry.mjs
```

This reads the actual root registry and preservation baseline, writes `actual-registry-validation.json` and `actual-release-review.json`, and performs no deployment or financial request. Exit code 0 means the complete release evidence passed; 1 means the registry/baseline is invalid; 2 means the registry is valid but release remains closed. An all-pending registry is expected to produce 2, which is a blocked activation, not a claim that games passed.

The standalone validator tests run with:

```sh
node --test codex-work/new-games72-20261121/release/release-gate.test.mjs
```

Actual source inventory verification and synthetic validator tests are recorded separately. Neither replaces the required per-game reference, gameplay, financial, browser or live verification.
