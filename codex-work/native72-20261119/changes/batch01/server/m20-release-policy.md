# Multi Hot 20 independent operator release policy

This is an explicit future **M20-only r3** path in the existing Railway service.
It does not enable the deployed r2, deploy anything, create services or wallets,
or authorize test tools to place production wagers. The checked-in
`m20-release-acceptance.json` is **PENDING**.

The user's existing instruction authorizes the operator's own probability model
and completion of this project. The release record documents verification under
that authorization; it does not require another user confirmation or pretend
that the provider's private RNG was reproduced.

## What remains immutable

- `independent-operator-audit.json`, `independent-release-pins.json`, and
  `independent-registry.mjs` keep their existing candidate semantics and hashes.
- Candidate `productionApproved` and `probabilityModelAudited` remain false.
- `providerRngReproduced` and `providerCertified` remain false in every profile.
- Burn Wilds remains unapproved and unavailable for new wagers.
- `railway-release/function-r2.tsx` and `release-r2.json` are frozen historical
  artifacts. The default builder reproduces those exact bytes, using their
  existing helper snapshots rather than today's edited helper source.

After verification, `createM20ReleasePolicy()` creates a deeply frozen M20 copy
with release approval metadata and the exact same strips, wheel weights, payout
rules, math hash and expected return. `auditReference` names the SHA-256 of the
reviewed acceptance record. It never mutates the original candidate.

## Record and evidence contract

All five evidence kinds are required: `unit`, `real-postgres`, `browser`, `source`
and `operator-policy`. Each uses two files in a review directory:

```text
unit.json                 unit.raw
real-postgres.json        real-postgres.raw
browser.json              browser.raw
source.json               source.raw
operator-policy.json      operator-policy.raw
```

The `.raw` file is the actual retained report, CI result/log, source review, or
existing authorization record. It is never generated by marking a checklist
successful. The `.json` file is a reviewed normalization of that artifact. Both
byte hashes are recorded in `record.evidence[kind]`:

```json
{
  "sha256": "SHA256_OF_NORMALIZED_JSON_BYTES",
  "rawSha256": "SHA256_OF_ACTUAL_RAW_EVIDENCE_BYTES",
  "reference": "actual CI run / artifact / repository evidence reference"
}
```

A normalized report has this common envelope:

```json
{
  "schema": "zplay-m20-release-evidence-v1",
  "kind": "unit",
  "gameId": "fresh_multihot20",
  "status": "PASS",
  "sourceCommit": "EXACT_TESTED_40_HEX_COMMIT",
  "sourceSha256": "EXACT_REVIEWED_SOURCE_SNAPSHOT_SHA256",
  "mathSha256": "4b7af42145bca5e7aa18a6d058c7394381d8b9b252110bffc61503c0470643d8",
  "rawSha256": "SHA256_OF_ACTUAL_RAW_EVIDENCE_BYTES",
  "reference": "same reference as the acceptance record",
  "recordedAt": "ACTUAL_UTC_TIMESTAMP",
  "checks": {}
}
```

The required `checks` keys are exported as `REQUIRED_CHECKS`. Each must be true
because its actual evidence was examined. The verifier checks integrity, scope,
source identity and completeness; it does not independently rerun the evidence
or prove that a human/agent's attestation is truthful. Preserve the original raw
artifacts and record only observed results.

## Exact source identity

`REQUIRED_SOURCE_PATHS` lists every required source relative to `batch01/`,
including backend helpers, the policy and builder, M20 app/controller/session/
scene/assets, artwork manifest, HTML/CSS and the existing Player route module.
`record.sources` maps each path to its actual SHA-256. Additional safe relative
source paths may be pinned too. `sourceSnapshotSha256(record.sources)` produces
the canonical sorted manifest hash used by every evidence report.

All reports must reference the same tested commit, snapshot and M20 math. A
later code edit invalidates the snapshot; it cannot reuse old evidence merely
by changing the record's hash. The source commit must actually contain those
bytes. A mixed working directory is not a verified commit.

The future package retains the exact reports and frontend/build source snapshots
for integrity verification. At startup it re-reads its executable backend helpers
and rejects drift. Frontend snapshots attest which source was reviewed; they do
not remotely inspect the currently live Worker. Publishing and reading back that
exact frontend artifact remains part of the surrounding release procedure.

## Complete the record only from observed acceptance

1. Freeze the intended source revision and collect the actual unit, real
   PostgreSQL, browser and source-review outputs for those bytes. Record known
   scope limits in the retained raw evidence.
2. Confirm that the PostgreSQL run exercises `createNative72Batch01Binding()`
   with the accepted policy, not solely hand-flipped profile flags. Synthetic
   policy fixtures are appropriate to exercise this path in the disposable
   test environment. Their generated attestations are test inputs, never actual
   release approval or substitutes for the resulting test report.
3. Review and normalize the five artifacts without fabricating missing checks.
   Save both normalized reports and their raw evidence bytes.
4. Fill the record's exact source commit/hash manifest, evidence hashes and
   references, reviewer identity, and actual UTC acceptance time. Evidence
   timestamps must not be later than acceptance. Set `decision: "ACCEPTED"`
   only after all required checks pass. No provider certification is required
   or asserted for this explicitly independent model.
5. Build the future package with the record and evidence directory explicitly:

```sh
node codex-work/native72-20261119/changes/batch01/server/railway-release/build.mjs \
  /path/to/exact-retained-runtime.mjs \
  /path/to/reviewable-r3-output \
  /path/to/reviewed-m20-acceptance.json \
  /path/to/reviewed-evidence-directory
```

The runtime input may be the pinned original baseline or the exact deployed r2
runtime (`23d14712d193519d9878fd956c6429bf739d45e5593d92904dce027cc4446f48`).
The builder rejects any other runtime, a PENDING record, missing/failed/drifted
evidence, or changed executable helpers before writing a release package. Its
output report says `deployed: false`, `m20ApprovalPackaged: true` and
`globalAcceptingGatePreserved: true`. M20 is the only game approved by the
package; new wagers still require the existing service's global accepting gate.
No build operation deploys that package.

With just the first two arguments, the builder always reproduces frozen closed
r2. There is no environment variable or request parameter that activates r3.

## Verification and recovery

Run `node --test server/m20-release-policy.test.mjs` from `batch01/`, plus the
existing server suites. The policy tests include a clearly synthetic accepted
record solely in temporary test files. They prove M20-only promotion, immutable
candidates, failed/missing/changed evidence rejection, existing-ledger replay,
global stop behavior, frozen r2 reproduction and r3 package startup validation.
They are not the real PostgreSQL or browser acceptance artifacts.

The existing service's global `accepting` switch, authenticated session, house
reserve, account balance limits, active-round ownership, latest-parent checks
and idempotency remain authoritative after approval. Stopping new wagers does
not remove read-only settled-round replay. Rollback uses the exact already
deployed r2 package; stored receipts and the existing wallet remain intact.
