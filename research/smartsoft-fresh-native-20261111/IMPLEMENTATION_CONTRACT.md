# Fresh independent machine implementation contract

The existing website is the destination. Rejected game frontends, old user media and previous engine definitions are not reference inputs for this rebuild. Each title is sourced from its own freshly opened official SmartSoft demo.

A title's reference package must identify the original page, native launch, source hashes, rendered screenshots, real native control actions, original sound resources, animation assets, responsive scene geometry and observed round transitions. A Play click alone is not a settled round. A loader, access restriction or empty canvas is not gameplay. Missing states remain explicit. Public framework declarations do not prove a feature is active in a title.

Build each machine from its own assets, configuration and observed state transitions. Use actual sprite/Spine animations, masks, blur frames, fonts and native layout constraints. A screenshot or prerecorded video must never serve as the playable surface. Do not replace missing symbols with emoji or reuse the rejected common CSS layout. Common rendering libraries are acceptable; title behaviour and visual configuration must be specific and evidence-backed.

The existing account and ETB ledger remain the financial integration. New independent mathematical models require explicit versions and their own payout/feature tests. Do not overwrite historical model definitions, pending request records or balances. RNG and settlement are server-authoritative; the browser only presents validated receipts. STOP changes the animation lifecycle and never submits another wager. An unknown server response keeps the same idempotency request for recovery. Presentation fixtures are not evidence of a real production wager.

Keep these claims separate: observed visual similarity; native controls tested; independently implemented mathematics; official provider integration. Public demos do not supply SmartSoft's private server source. Do not label independent models as the original provider engine or claim 100% identity.

Before each existing website route is replaced, compare the new machine against its fresh official reference at mobile portrait, mobile landscape and desktop sizes. Validate every implemented button, normal spin, stop, sound/music, bet dialog, rules, history, bounded autoplay, win/collect/gamble and each supported special feature. Record rare features not yet observed rather than claiming them verified. Preserve the accepted original MultiHot5 and FoxyHot20 routes unless the user explicitly changes that exception.

No new reference website, archive dashboard, duplicate placeholder card or alternative hosting destination. Integrate reviewable completed machines into the existing Cloudflare Worker routes and existing backend.
